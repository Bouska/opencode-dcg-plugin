# AGENTS.md

OpenCode plugin that blocks destructive shell commands by shelling out to the
[`destructive_command_guard`](https://github.com/Dicklesworthstone/destructive_command_guard)
(dcg) binary. Thin adapter — all rule/pack configuration is dcg's job, not ours.

User-facing install/usage docs live in `README.md`. This file is for agents
working in the repo.

## Stack

- Bun (1.3.x, pinned in CI and `bun-types` devDep) + TypeScript 5.7+ ESM.
- No bundler config, no linter, no formatter. `tsc` + `bun build` only.
- Single workspace. No monorepo packages.
- OpenCode plugin API v1.17+ (`engines.opencode`).

## Source layout

- `src/index.ts` — plugin entry (`DcgGuard`, also exported as `default`).
  Hooks `tool.execute.before`, parses config, probes dcg, calls `runDcg`,
  formats block messages, optional LLM review handoff.
- `src/review.ts` — optional LLM review feature. **Not** a standalone plugin,
  but it ships a no-op `default` export so OpenCode's v1.17+ plugin loader
  doesn't iterate its named exports (`buildUserPrompt`, etc.) as if they
  were plugins and crash on the first hook call. If you add a new file with
  named function exports that the bundler can also see as a plugin, give it
  the same `{ id, server: async () => ({}) }` sentinel.
- `test/index.test.ts`, `test/review.test.ts` — bun test, plain imports of
  `../src/index.ts` (no transpile step).

## Commands

```bash
bun install
bun run typecheck    # tsc --noEmit
bun test             # unit + dcg integration
bun run build        # produces dist/opencode-dcg-plugin.{js,d.ts}
```

There is no `lint` or `format` script. Don't invent one.

Run a single test file: `bun test test/review.test.ts`. Run a single test by
name: `bun test -t "denies rm -rf"`.

## dcg is a hard test dependency

`test/index.test.ts` has `describe.skipIf(!Bun.which("dcg"))` around the
`runDcg` integration block. Without `dcg` in `PATH`, those cases silently
skip — you only get the unit tests. CI uses Ubuntu + the maintainer's
dev environment, so install dcg before assuming the test suite is green:

```bash
curl -fsSL https://raw.githubusercontent.com/Dicklesworthstone/destructive_command_guard/main/install.sh | bash -s -- --easy-mode
```

`dcg --version` should print a banner with a version string.

## Build is non-obvious — read the script before changing it

`package.json` `build`:

1. `rm -rf dist`
2. `tsc --emitDeclarationOnly --outDir dist` (tsconfig has `emitDeclarationOnly: true`)
3. `mv dist/index.d.ts dist/opencode-dcg-plugin.d.ts` — the published
   type entry is renamed because the runtime entry is renamed next.
4. `bun build src/index.ts --outdir=dist --entry-naming=opencode-dcg-plugin.js --target=node --format=esm --sourcemap=linked`
5. `rm dist/review.d.ts` — review is inlined into the single bundle; the
   stray `.d.ts` would otherwise be shipped.

Output: a single ESM file `dist/opencode-dcg-plugin.js` (with a linked
sourcemap `dist/opencode-dcg-plugin.js.map`) + one `.d.ts`. The plugin
loaders look for the `.js` filename; renaming breaks Option A/B installs.
Review is inlined — do not add a second entrypoint unless you also update
the load path.

## Config is environment-driven at runtime

All plugin behavior comes from `DCG_PLUGIN_*` env vars parsed in
`loadConfig()` (`src/index.ts:248`). There is no `opencode.json` schema
contribution from this plugin.

`envBool` deliberately matches dcg's own `parse_env_bool`:
`1|true|yes|y|on` (trim, case-insensitive). Don't change one without
the other — divergence silently desyncs the plugin from dcg's bypass
detection. Same goes for `DCG_BYPASS` itself, which is read from
`process.env` at init and snapshotted into `config.dcgBypass`. The
model cannot flip it from a child process. A command starting with
`DCG_BYPASS=1` is still sent to dcg, which evaluates the full string
and denies the dangerous part.

## Review feature gotchas

`DCG_PLUGIN_REVIEW_ENABLED` requires an OpenCode LLM subsession. The
default agent is `general` — if the user has `agent.general.disable: true`
in their OpenCode config, the review fails and the command stays blocked
(safe default). Either re-enable `general` or set
`DCG_PLUGIN_REVIEW_AGENT` to an enabled agent.

The review feature defaults to disabled (`DCG_PLUGIN_REVIEW_ENABLED=false`)
for a reason — see the "Security note — prompt injection" block in
`README.md` before turning it on in any environment where the conversation
history isn't fully trusted.

When enabled, the review LLM receives recent parent-session messages as
context (`DCG_PLUGIN_REVIEW_CONTEXT_MESSAGES` / `_MAX_CHARS`).

## Repo-local dcg config

The repo has a `.dcg/allowlist.toml` (gitignored, generated by dcg
when the user runs `dcg allow` locally). It is **not** the project's
dcg config — that's `.dcg.toml` at the repo root, and there is none
checked in. If a test or feature appears to need allowlist entries,
the user owns that file; do not commit `.dcg/`.

## Commit messages

Soft guidance, not enforced — the repo has no commitlint, husky, or
commit-msg hooks, and CI does not lint history. Past commits are mixed
(some CC-prefixed, some freeform imperative); pick what fits the change.

**Subject line**
- Imperative mood: "Add OAuth login" not "Added" or "Adding". Completes
  the sentence "If applied, this commit will ___".
- Capitalized, no trailing period. ≤50 chars (72 hard cap).
- One commit = one coherent change. If a diff has two unrelated purposes,
  split it.

**Style**
- Plain freeform is fine for this repo's size.
- A `type:` or `type(scope):` Conventional Commits prefix is also fine
  when it helps — `feat`, `fix`, `docs`, `chore`, `refactor`, `test`,
  `ci`, `build`. Don't force it on small tweaks.
- A colon in the subject is usually a code-symbol reference, not a CC
  prefix. E.g. `envBool: match dcg's parse_env_bool (trim + add y/n)`
  is freeform — the colon is part of the function signature.

**Body** (when the subject alone isn't enough)
- Blank line between subject and body. Wrap at ~72 chars.
- Explain *what* and *why*, not *how* (the diff shows *how*).
- `Closes #N` / `Refs #N` footers for issue links.

**Version bumps** are an exception: `npm version` produces a short
commit like `0.3.1` — no subject, no body. Don't rewrite it.

## Release flow

Triggered by pushing a `v*.*.*` tag. CI (`.github/workflows/release.yml`):

`bun install --frozen-lockfile` → `typecheck` → `test` → `build` →
verify tag matches `package.json` version → `npm publish` (OIDC
trusted publishing, no `NPM_TOKEN` secret) → `npm pack` →
GitHub Release with the tarball attached.

Local release is the standard `npm version {patch|minor|major} &&
git push --follow-tags`. `npm publish` is not idempotent — a re-run
of the workflow fails at the publish step if the version already
exists on npm.

## What an agent is likely to miss

- The single-file build is load-bearing. Don't split into multiple entries
  or change the output filename without updating README install paths.
- `review.ts` must keep its no-op `default` export. Removing it produces
  harmless-but-noisy `level=ERROR` lines in OpenCode's logs.
- `strictMissing` (`DCG_PLUGIN_STRICT_MISSING=true`) is opt-in for a
  reason: the dcg probe runs async with a 2s cap, so the first 1–N
  commands can race past the probe when dcg is slow to start. The
  default (`throw once, then fail-open`) is the right default.
- `dist/`, `node_modules/`, `.dcg/`, and `*.log` are gitignored. Don't
  commit any of them.
- No `.opencode/`, `opencode.json`, or `AGENTS.md` other than this one
  is expected at the repo root. If you add one, document why.
